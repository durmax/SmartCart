# Retailer offer-source assessment

## Decision

No source was verified that combines documented permission for SmartCart to consume offers, a stable interface, and supported browser access with dependable product, price, validity, and restriction data. No real retailer provider is implemented. The Shopping Planner continues to show explicitly labeled synthetic development examples; they are not current retailer prices and are not eligible for comparisons.

ALDI SÜD remains the preferred source for the Neuss area if the retailer authorizes an integration. Lidl Germany is also not currently suitable. Do not use either consumer page as a scrape target, and do not implement the undocumented ALDI endpoint described by the research project below without written authorization and a supported interface.

## Findings and blocker

- A public consumer page, an unauthenticated response, or an open-source client does not establish permission for automated reuse. No public official API documentation, explicitly authorized third-party feed, or project-specific authorization was identified in this review.
- Browser CORS has not been demonstrated for an offer-data interface. Lidl's homepage response did not include `Access-Control-Allow-Origin`; ALDI SÜD returned 403, so its CORS behavior could not be checked. The ALDiscount API is undocumented and its CORS behavior is unknown.
- Offer data must identify product/variant and package, price, retailer-published validity, retrieval/source, geographic/store availability, and any loyalty or other restrictions. No reviewed source offered a verified stable contract for all those fields. In particular, ALDiscount infers an end date rather than receiving it from ALDI.
- The exact blocker is a missing retailer-approved offer API/feed and its access terms, together with supported browser CORS or an approved server-to-server access method. Until supplied and verified, SmartCart cannot truthfully retrieve and compare real current/upcoming retailer prices.

## Lidl server-side connectivity PoC

- Tested URL: `https://offers.lidlplus.com/app/api/v4/DE/DE5868/offers`. The project owner reports that opening this URL directly returned JSON, while a browser `fetch()` from `https://localhost:7035` was blocked because Lidl's response did not include the required `Access-Control-Allow-Origin` header.
- PoC route: `GET https://localhost:7297/api/lidl/offers?storeKey=DE5868`. In Development only, SmartCart.Api sends the fixed Lidl HTTPS URL with HTTP/2 (`RequestVersionExact`), `Accept: application/json`, and `Accept-Language: de-DE`, then returns a successful JSON response without reshaping it. The store key is restricted to `DE` followed by digits; callers cannot supply an upstream URL. SmartCart.Api's named CORS policy allows the configured Web origin (`Cors:AllowedOrigins` in `appsettings.Development.json`), not arbitrary origins.
- Upstream test result: the project owner reports that HTTP/1.1 and HTTP/2 without the two added headers returned **HTTP 400**, while HTTP/2 with both headers returned **HTTP 200 and nonempty offers JSON**. This is user-reported local evidence; it was not retested for this documentation change. The number of offers and their product/price/date fields were not supplied. Both headers are retained as a tested combination; whether each is individually required is unknown.
- To run locally: `dotnet run --project src/SmartCart.Api --launch-profile https`, then request `https://localhost:7297/api/lidl/offers?storeKey=DE5868` with a browser or `Invoke-RestMethod`. Confirm the upstream status from API logs and inspect `offers`, titles, price fields, and validity dates in the returned JSON. From the Web browser console, test `fetch('https://localhost:7297/api/lidl/offers?storeKey=DE5868').then(r => r.json()).then(console.log).catch(console.error)` while `https://localhost:7035` is open.
- This endpoint is an unofficial, development-only experiment—not an open proxy, supported Lidl API, or authorization to reuse the data. Production use requires checking Lidl's applicable permissions, terms, rate limits, and intended data use. No login credentials, retries, browser automation, proxy rotation, persistence, or offer matching are implemented. Lidl may reject server-side traffic or change the undocumented response; valid-looking JSON does not establish permission or product-ID/price semantics. Browser CORS failures and upstream HTTP 400 responses are separate issues: changing SmartCart.Api CORS cannot correct an upstream rejection.

The next step for any production integration remains obtaining written authorization and official feed/API terms, including allowed retrieval, display, rate/retention, and regional/store usage. A server-side request addresses browser CORS only when server-side access is permitted; it does not itself grant permission or provide a stable data contract.
